## Как использованы навыки из домашних заданий

Итоговый стенд не копирует все учебные стенды буквально. В него вошли те решения, которые подходят для защищённого веб-сервиса. Остальные технологии сохранены как варианты расширения, если их применение не даёт пользы именно этой архитектуре.

| Задание | Что перенесено в итоговый проект |
| --- | --- |
| 1. Ядро | Работа с базовым Linux-образом и проверка служб после загрузки. |
| 2. RAID | Идея отказа одного устройства; в финальном проекте отказоустойчивость реализована на уровне edge, приложения и БД. |
| 3. LVM | Разделение системных и прикладных данных учитывается при планировании backup-хранилища. |
| 4. ZFS | Принцип контрольного хранения и восстановления применяется через Borg, а ZFS не добавлен из-за привязки к конкретной ОС. |
| 5. NFS | Изучен общий доступ к файлам; в WordPress оставлено локальное хранение, чтобы NFS-сервер не стал единой точкой отказа. |
| 6. Пакеты | Установка служб через штатный пакетный менеджер Ansible. |
| 7. GRUB | Учитывается жизненный цикл ВМ и проверка загрузки после перезапуска. |
| 8. Systemd | Все основные службы включаются в systemd, backup запускается таймером. |
| 9. Bash | Небольшие служебные сценарии используются для backup и проверок состояния. |
| 10. Процессы | Состояние процессов проверяется через systemd, Prometheus и команды диагностики. |
| 11. SELinux | В итоговом Ubuntu-образе используется AppArmor; правила SELinux из отдельного задания не переносятся механически в другую систему. |
| 12. Ansible | Весь стенд настраивается ролями Ansible. |
| 13. Vagrant | Все ВМ и изолированные VirtualBox-сети описаны в Vagrantfile. |
| 14. Docker | Стек Prometheus, Alertmanager, Blackbox и Grafana запускается через Docker Compose. |
| 15. Prometheus | Собираются CPU, память, диск, сеть и доступность HTTPS. |
| 16. PAM | Доступ к edge ограничен сетями управления; выходные ограничения из учебного задания не применяются к веб-сервису. |
| 17. Logging | Rsyslog принимает удалённые логи и сохраняет их по именам хостов. |
| 18. Borg | Backup WordPress, конфигурации Nginx и дампа базы шифруется и запускается по systemd timer. |
| 19. Сетевая архитектура | Внешняя сеть, DMZ и backend разделены разными VirtualBox internal network. |
| 20. DHCP/PXE | Для итоговой демонстрации не требуется: адреса узлов стенда фиксированы и задаются Vagrant. |
| 21. Iptables | На edge включён входной firewall с политикой `DROP`. |
| 22. Routing | Маршрутизация заменена reverse proxy и разделением сетей, потому что отдельный OSPF-стенд не нужен для этой схемы. |
| 23. VPN | Доступ к лабораторной сети выполняется через Vagrant; VPN можно добавить как внешний канал управления без изменения веб-трафика. |
| 24. DNS | Для локальной проверки используется имя `web.local`; сертификат и WordPress настроены на это имя. |
| 25. VLAN/LACP | Изоляция сделана отдельными internal network; LACP в виртуальной демонстрации не даёт практической пользы. |
| 26. LDAP | Системные пользователи стенда не являются частью приложения, поэтому FreeIPA не добавлен в критический путь. |
| 27. Dynamic Web | WordPress работает через Nginx и PHP-FPM на двух application-узлах. |
| 28. MySQL | Практика репликации продолжена через MariaDB Galera: приложение получает единый локальный endpoint HAProxy, а данные синхронны между тремя узлами. |
| 29. PostgreSQL | Практика standby и резервного копирования учтена в схеме отказа БД и Borg-восстановлении; WordPress использует MariaDB. |
